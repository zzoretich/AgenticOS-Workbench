# Phase 6: ship 1.0.0 — plan

Design: `docs/superpowers/specs/2026-10-05-workbench-app-design.md` (D1, D3, D9, D13). Parent plan:
`docs/superpowers/plans/2026-10-05-workbench-app.md` (phase 6). Verified against `ce7075f`.

## Where it starts

`main` carries phases 1–5; nothing is released (the last tag is v0.21.0). The docs still say the app's download
"arrives with 1.0" (README ×2, `docs/install.md` ×2, the CLI's checklist, the CHANGELOG). `release.yml` builds the
Obsidian bundle (`obsidian-plugin/esbuild.config.mjs` → `main.js`) and attaches `main.js`, `manifest.json` and
`styles.css`; nothing else uses that bundle (`tokens.ts` is committed, and the app compiles the HUD's source). The app
reads `obsidian-plugin/manifest.json` three times: `app/scripts/build.mjs` (`@workbench/hud-manifest`), `boot.ts` (the
plugin's id, name and version) and `check-compat.mjs` (the version it prints). `tools/bump-version.js` lists
`manifest.json` and `versions.json` (Obsidian's `minAppVersion` map) as version surfaces. New vaults get
`vault-template/.obsidian/` (four files, one enabling `agentic-os`). The app reads the HUD's settings from its data
folder, else from the Obsidian-era `<vault>/.obsidian/plugins/agentic-os/data.json`, and saves its own copy only when a
setting changes: a user who removes that folder as told would lose their settings.

## Decisions

| # | Decision | Rejected |
|---|---|---|
| R1 | **The app owns the HUD's identity.** `boot.ts` builds the compat manifest itself: id `agentic-os` and name `Agentic OS` as fixed values (the id keys the HUD's settings file, the Obsidian-era settings it carries over, its command ids and CSS class), the version from `obsidian-plugin/package.json`, which is already a bumped surface. The alias becomes `@workbench/hud-package`, imported by name so the bundle keeps only `version`. `check-compat` prints the same version | Keeping `manifest.json`: an Obsidian plugin manifest (`minAppVersion`, `isDesktopOnly`) nothing installs, and one more version surface. Deriving the id from the package's `name`: a rename of an npm package would move every user's settings |
| R2 | **Drop the Obsidian packaging, keep the HUD's source.** Delete `manifest.json`, `versions.json`, `esbuild.config.mjs` and `scripts/rebuild-pty.mjs`; drop the `build`, `dev` and `rebuild-pty` scripts, the `main` field and the devDependencies only they used (`esbuild`, `builtin-modules`, `@electron/rebuild`). The `main.js` ignore lines stay, so a bundle an older checkout built stays out of git, the gate and lint. `main.ts`, `src/`, `styles.css`, `gen:tokens`, `typecheck`, `test` and the `obsidian` types (D5) stay | Keeping an Obsidian build no release ships (D1) |
| R3 | **`release.yml` publishes the notes only.** The build job keeps the version check, the CHANGELOG check, the gate and the HUD's typecheck and tests; its artifact is `release-notes.md`. The publish job creates the release with no assets, and a re-run only refreshes the notes, so it never touches what `release:app` uploaded (DMG, zip, blockmap, `latest-mac.yml`) | Building the app in CI: signing stays on the maintainer's Mac (D9) |
| R4 | `bump-version` drops `manifest.json` and `versions.json`; `obsidian-plugin/package.json` and its lockfile entry stay surfaces | — |
| R5 | **Settings carry over.** When the app has no settings file of its own and reads the Obsidian-era `data.json`, it saves that copy into its data folder at once (best effort), so removing `.obsidian/plugins/agentic-os/` loses nothing. The vault file is still never written | A note in the migration guide to change a setting first: a trap for everyone who skims it |
| R6 | **New vaults are plain.** `vault-template/.obsidian/` is no longer seeded; an existing vault's `.obsidian/` is left alone. The `.gitignore` and `.graphifyignore` rules for `.obsidian/` stay: they cost nothing and keep Obsidian's churn out for anyone who still opens the vault there | Removing `.obsidian/` from existing vaults: it is the user's, and may hold other plugins |
| R7 | **The download link is the releases page** (`…/releases/latest`), named by the CLI's checklist (a checkout install) and by `aos upgrade`'s one line to an Obsidian-era vault. The app is built for Apple silicon (`AgenticOS-Workbench-<version>-arm64.dmg`), and the docs say so | Naming a versioned DMG URL: stale after the next release |
| R8 | **Docs app-first.** README and `docs/install.md`: download → wizard is the main path, the terminal second. `docs/migrating-to-1.0.md` for Obsidian-era users. `docs/plugin-smoke.md` becomes `docs/app-smoke.md`: Obsidian-only rows are rewritten in place to the app's equivalent (so `COVERAGE.md`'s ids hold), the Term install rows go, and the release procedure gains `release:app`. `docs/acceptance.md`: the fresh-account run starts from the DMG and the wizard (no Obsidian, no `--terminal`), and gains the update run from the previous build. Descriptions and leftovers: the marketplace, both `package.json`s, the Codex plugin's generator, `AGENTICOS.md`, `docs/chief-of-staff.md`, `obsidian-plugin/README.md` | — |
| R9 | **CHANGELOG.** `[Unreleased]` opens with one line pointing at the migration guide (an absolute link: the section is the release notes); **Upgrading** says install the app, then the runtime upgrade (the app's offer or `aos upgrade`) and `aos routines sync`, then remove the old plugin folder; the app entry loses "not released yet"; Removed gains the release assets and the `.obsidian/` seed | — |

## Tests

- Unit: `bumpFiles`/`checkFiles` over the remaining surfaces (no `versions.json` row); `loadPluginData` copies a legacy
  file once, prefers the app's own, and survives an unwritable data folder.
- CLI: `aos init` seeds no `.obsidian/`; the checklist names the download; `aos upgrade`'s line names it too.
- Rehearsals: `first-run.sh` asserts no `.obsidian` at all; `codex-host.sh` unchanged.
- App: typecheck, unit, `check:compat`, the e2e suite (the settings window's "Agentic OS" tab, the HUD version in App
  Settings), `dist:test` + `smoke:packaged`, a release-config `--dir` build with `dist:verify --app-only`.

## Host parity

Nothing in a hook, skill, MCP tool or model call changes. The Codex plugin's manifest text changes through its
generator (`npm run build:codex-plugin`). The wizard and the docs name both hosts' steps (the `CLAUDE.md` line, the
`/hooks` trust step).

| Mode | How the user gets 1.0 | What runs | If it can't |
|---|---|---|---|
| Claude Code only | the DMG → the wizard (`--host claude`), or `aos upgrade` | app + runtime + Claude Code plugin | the wizard's fix-its; the terminal path |
| Codex only (plugin · direct) | the same, `--host codex` | app + runtime + Codex plugin or direct wiring | same |
| Both | the same, `--host both` | both | same |

## Exit

The PR merged with every check green. Then, with the owner's go-ahead: the bump to 1.0.0, the tag, `release.yml`'s
notes, `release:app`'s DMG, zip and feed, and the acceptance run (`docs/acceptance.md`: the update from the previous
build on the maintainer's Mac, and a fresh account from the DMG with no terminal), recorded in that file.
